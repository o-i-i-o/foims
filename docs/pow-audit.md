# 登录保护机制审计：PoW（工作量证明）建议的评估结论

日期：2026-08-24
背景：有外部建议为 IPMA 登录引入 PoW（Proof of Work，工作量证明）作为防爆破手段。
本文档记录对该建议的审计过程与落地决策。

## 1. 威胁模型

登录接口面临的攻击按成本递增：

1. **单账户低速爆破**：攻击者对少数账户周期性尝试口令。
2. **单账户高速爆破**：脚本对单账户高频尝试。
3. **分布式撞库（credential stuffing）**：多来源、多账户、低频次，规避按 IP 限速。
4. **接口洪泛（DoS）**：以消耗服务端资源为目的的请求洪水。

## 2. PoW 能解决什么、不能解决什么

PoW 的机制是让客户端在提交登录前完成一次计算难题（如寻找 SHA-256 前缀为零的
 nonce），服务端校验后放行。

**能缓解**：场景 4 中纯脚本发起的零成本请求洪水（提高每次请求的客户端单价）。

**不能解决**：
- 场景 1/2/3 的口令猜测本身——攻击者只需为"值得尝试"的口令付计算成本，
  现代浏览器 WASM/Worker 计算 SHA-256 的速率达每秒数十万次，常规难度
  （≤2²⁰）对自动化工具几乎无感，而对低端设备用户造成可感知的延迟与耗电；
- PoW 挑战本身可被脚本批量预计算后缓存使用（除非做严格的单次挑战绑定，
  而这又引入与验证码相同的状态管理复杂度）；
- 服务端校验虽然便宜，但生成与分发挑战仍占用带宽与连接，对 DoS 的
  抑制作用远不如边缘层（nginx `limit_req`）限速。

## 3. IPMA 已部署的纵深防御

| 层级 | 机制 | 位置 |
| --- | --- | --- |
| 边缘 | nginx 速率限制 | `deploy/nginx` |
| 请求级 | 加权滑动窗口限流（登录路径 5/60s，邮箱路径 5/h） | `src/utils/rate_limit.rs` |
| 失败计数 | 应用层 fail2ban（IP + 用户名双维度，5 次封禁 30 分钟） | `src/system/app_fail2ban.rs` |
| 人机区分 | **连续 3 次失败触发图形验证码**（本次新增，复用 fail2ban 计数） | `src/auth/captcha.rs` |
| 口令强度 | 等保密码策略（复杂度/有效期/历史重复） | `src/auth/password_policy.rs` |
| 会话 | 设备指纹绑定 JWT、令牌吊销、角色变更强制下线 | `src/auth/*` |
| OS 层 | fail2ban 监控 `/var/log/ipma/auth.log` | `deploy/fail2ban` |

验证码在"3 次失败后出现"的设计恰好覆盖 PoW 想覆盖的场景 2/3：自动化脚本
在触发阈值后必须解决图形识别问题，其成本远高于计算一个哈希。

## 4. 结论

**不引入 PoW。** 理由：

1. 对目标威胁（口令爆破/撞库）无效，对附带威胁（DoS）有更合适的层（nginx）；
2. 全量用户支付延迟/耗电成本，换来的防护可被脚本以廉价 GPU/WASM 计算
   绕过，收益成本比为负；
3. 已落地的"失败触发验证码 + 双维度 fail2ban + 限流"组合在效果上严格
   优于低难度 PoW。

若未来实测出现 HTTP 层洪泛，应优先在 nginx 启用 `limit_req` 区域化限速与
连接数限制，而非在应用层叠加 PoW。

## 5. 已实现的替代方案摘要

- `GET /api/auth/captcha`：公开图形验证码（SVG、5 分钟有效、一次性、
  大小写不敏感、字符集去混淆）；
- 密码/LDAP 登录：服务端依据 fail2ban 失败计数（阈值 3）强制校验验证码；
- 前端：第 3 次失败后主动显示验证码输入与图片（点击刷新），
  与服务端强制互为兜底。
